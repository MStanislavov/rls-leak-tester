# ADR draft: GitHub Actions CI and Dependabot

- Status: proposed (draft, numbered by the orchestrator)
- Date: 2026-09-20
- Phase: 8 (task C)
- Builds on: ADR 0001 (Node and npm), 0017 (Redis contract suite), 0019 (the exported workflow),
  0021 (the self-isolation proof)

## Context

Brief 5.3 asks for a workflow with install and cache, lint, type-check, rules check, unit tests
with coverage and a Redis service, build, Playwright, the self-isolation proof on a Postgres
service, and a Sonar scan with a quality gate that skips cleanly without a token; plus Dependabot
for npm and for Actions. A fresh fork with no secret must be green.

Files: `.github/workflows/ci.yml`, `.github/dependabot.yml`, `tests/ci/workflow.test.ts`.

## Decisions

1. **Five jobs, named after the promise they keep**: `static` (lint, typecheck, rules,
   format:check as four steps that each run even when an earlier one failed, so one run shows
   everything), `unit`, `e2e`, `self-isolation`, `sonar`. Only `sonar` has a dependency
   (`needs: unit`, for the LCOV artifact). Every job: `ubuntu-24.04`, a timeout, checkout with
   `persist-credentials: false`, `actions/setup-node` with `cache: npm`, `npm ci`.
2. **Frame**: `push` to `main` and `pull_request`; `concurrency` per workflow and ref with
   `cancel-in-progress: true`; top-level `permissions: contents: read` and no job widens it;
   `defaults.run.shell: bash` (GitHub then runs `bash --noprofile --norc -eo pipefail`); no
   `${{ }}` inside any `run:` block (values reach the shell as environment variables only).
3. **Actions pinned by commit, release in a comment** (read with `git ls-remote --tags` on
   2026-09-20, inputs read from each `action.yml` at that commit, all `using: node24`):
   `actions/checkout` v7.0.1 `3d3c42e5aac5ba805825da76410c181273ba90b1`,
   `actions/setup-node` v7.0.0 `820762786026740c76f36085b0efc47a31fe5020`,
   `actions/upload-artifact` v7.0.1 `043fb46d1a93c77aae656e7c1c64a875d1fc6a0a`,
   `actions/download-artifact` v8.0.1 `3e5f45b2cfb9172054b4087a40e8e0b5a5461e7c`.
   All four tags are lightweight (no `^{}` entry), so the tag's SHA is the commit. The exported
   workflow (`src/lib/export/workflow.ts`) still names checkout v6.1.0; that file is another
   slice's and a user's copy is theirs to update.
4. **Node 24** (`NODE_VERSION: "24"`, today 24.21.0 "Krypton", the active LTS). Checked against
   `package-lock.json`: every `engines.node` range of a non-optional package accepts 24.21.0 and
   22.23.2; ADR 0001 allows both lines. 24 was chosen because it bundles npm 11.19.0, the npm of
   this machine, of the lockfile and of the `allowScripts` field (22.23.2 bundles npm 10.9.8).
   `npm ci` runs `prepare` (`scripts/hooks/install-git-hooks.mjs`): in a checkout it sets
   `core.hooksPath` and exits 0 in every branch, so it cannot break CI.
5. **unit**: service `redis:7-alpine` (the compose image) with a health check, port 6379
   published, `REDIS_URL=redis://127.0.0.1:6379`. Loopback on purpose: the network guard
   (TEST-001) refuses anything else, the service name included. `npm run test:coverage` enforces
   the thresholds of `vitest.config.mts`; `coverage/lcov.info` is uploaded as `coverage-lcov`
   (`if-no-files-found: error`).
6. **e2e**: `npx playwright install --with-deps chromium`, then `npm run e2e` (`next build`, then
   Playwright against `next start`, so the production Content-Security-Policy). On failure
   `playwright-report/` and `test-results/` (traces) are uploaded.
7. **self-isolation**: service `postgres:18-alpine`, asserted by the test to be `POSTGRES_IMAGE`
   of `@/lib/export`, the image the exported workflow tells users to run. Steps: generate the
   proof with `npx tsx scripts/self-isolation/generate.ts "$RUNNER_TEMP/self-isolation"`; make
   sure `psql` exists; wait for the server and print its version; ONE
   `psql --no-psqlrc -v ON_ERROR_STOP=1` with `--file` for the setup file, every
   `supabase/migrations/*.sql` (glob under `LC_ALL=C`) and the seed; then one `psql` for
   `rls-isolation.test.sql`, whose exit status is the job's. `PGTZ=UTC` as in the runner. No step
   has a condition and the file has no `continue-on-error`.
   - One session for setup, migrations and seed is what `setupDatabase` and the exported
     workflow do (ADR 0019, decision 5). `scripts/self-isolation/verify-postgres.sh` uses one
     session per file; both pass for this schema, the job follows the export.
   - The health check asks over TCP (`pg_isready --host 127.0.0.1`): the image's temporary
     start-up server listens on the socket only, so "healthy" means the real server.
   - The image is pinned to the major version by tag, not by digest: Dependabot does not update
     service images in workflows, and a stale digest would stop receiving 18.x fixes.
   - `ubuntu-24.04` ships PostgreSQL 16.15 with its service disabled (runner image README,
     image 20260907.300.1): `psql` 16 is there and port 5432 is free. The rehearsal used a
     `psql` 16 client for that reason.
8. **sonar**: the `secrets` context does not exist in a job-level `if` (actionlint confirms:
   `context "secrets" is not allowed here`). The first step maps `secrets.SONAR_TOKEN` into its
   own environment and writes only `has_token=true|false` to `GITHUB_OUTPUT` (plus a notice when
   it skips); every later step has `if: steps.sonar.outputs.has_token == 'true'`. Forks,
   Dependabot and a fresh clone get a green job that says it skipped. With a token: checkout with
   `fetch-depth: 0`, `npm ci`, download `coverage-lcov` into `coverage/`, then
   `npx sonar-scanner-npm -Dsonar.qualitygate.wait=true` (the binary name of the installed
   `@sonar/scan` 5.0.0; `sonar` and `sonar-scanner` were removed in v5).
   Read from the scanner's source, not remembered: it maps `SONAR_TOKEN`, `SONAR_HOST_URL` and
   `SONAR_ORGANIZATION` from the environment, and environment values win over
   `sonar-project.properties` even when EMPTY. So the optional values travel as
   `CI_SONAR_ORGANIZATION` / `CI_SONAR_PROJECT_KEY` (repository variables `SONAR_ORGANIZATION`,
   `SONAR_PROJECT_KEY`) and become `-D` options only when set; an absent `SONAR_HOST_URL` secret
   becomes `https://sonarcloud.io` explicitly.
9. **Dependabot**: `npm` and `github-actions`, weekly (Monday 06:00 UTC), at most 5 open pull
   requests each; npm minor and patch updates grouped into one pull request, majors alone; all
   action bumps grouped. Commit prefixes `build` / `ci` with `include: scope`, so the subjects
   (`build(deps): ...`, `build(deps-dev): ...`, `ci(deps): ...`) pass the commit-msg hook. Keys
   checked against the published schema (`json.schemastore.org/dependabot-2.0.json`).
10. **`tests/ci/workflow.test.ts`** (30 tests) parses both files with `yaml` and strict zod
    schemas (an unknown job key such as `permissions` or `continue-on-error` fails) and pins:
    triggers, concurrency, permissions, the five job ids, SHA-pinned `uses` with a version
    comment and one commit per action, `persist-credentials: false`, Node and `npm ci`, that
    every `npm run <script>` exists in `package.json`, the Redis and Postgres services,
    `REDIS_URL`, the one-session load and its order, the unconditional proof step, the sonar
    indirection (no `secrets.` in a job-level `if`, secrets only in step `env`, every later step
    conditional on `has_token`), `fetch-depth: 0`, the gate wait, and the Dependabot structure.

## Evidence (2026-09-20, macOS arm64, Docker 29.5.2, Node v26.8.1)

- **actionlint 1.7.12 with shellcheck 0.11.0: 0 errors** in `.github/workflows/ci.yml`.
  Sanity check of the linter on a scratch copy with two injected mistakes: it reported the
  job-level `secrets` expression and SC2086, exit 1.
  Deviation: the brief's `docker run rhysd/actionlint:latest` could not be used. Every
  `docker pull` on this machine hung without output (also `alpine:latest`; the registry answers
  `curl` within a second, so it is the Docker Desktop proxy). The official release binaries were
  used instead (actionlint checksum verified), which is what the image contains.
- **Rehearsal of job 4, steps taken verbatim from the parsed YAML** and run with
  `bash --noprofile --norc -eo pipefail`: `postgres:18-alpine` started with the job's
  `options` on a free host port, waited for `healthy` (6 s); the `psql` steps ran in a
  `postgres:16` container (`psql` 16, as on the runner) that shared the service's network
  namespace, so `PGHOST=127.0.0.1`, `PGPORT=5432` applied as written. Output:
  `own-scenarios-table-fixed: ISOLATED on PGlite, 20 cells exported`,
  `PostgreSQL 18.4 on aarch64-unknown-linux-musl`, the load step exit 0, 20 lines
  `NOTICE:  ok - ...`, `RLS Leak Tester: ISOLATED. 20 of 20 checked cells passed, 0 warnings.`,
  exit 0. Not rehearsed: the two `uses:` steps and `npm ci` (the working tree's `node_modules`
  were used, and the generate step ran on the host's Node 26, not 24).
- **Negative control, same steps**, with a copy of the migration mounted over
  `supabase/migrations` whose public read policy says `visibility in ('public', 'unlisted')`:
  the load step exit 0, then `ERROR:  RLS Leak Tester: LEAKING or not proven. 4 of 20 checked
cells failed, 16 passed`, the four declared select cells with leaked keys `...a2` / `...b2`,
  `psql` exit 3, the job fails at "Prove isolation". The containers were removed.
- **Sonar skip**, the first step run as written: empty token gives `has_token=false` and the
  notice, a non-empty one `has_token=true`, exit 0 both times. The scan step's argument building
  with the scanner replaced by `printf`: nothing set gives `SONAR_HOST_URL=https://sonarcloud.io`
  and `-Dsonar.qualitygate.wait=true`; with everything set the two `-D` options are added.
- `npx vitest run tests/ci`: 30 passed. `eslint`, `prettier --check`, `npm run rules`: clean.

## Not verified

- **No run on GitHub's runners**: nothing can be pushed from here. Verified are syntax and
  expressions (actionlint), structure (Vitest) and the behaviour of the shell steps of jobs 4 and
  5 (rehearsal). The service container start-up, the artifact hand-over and the caches are
  GitHub's.
- **No real scan from CI**: there is no SonarQube Cloud project. A self-hosted server must be
  reachable from GitHub's runners; the local compose server is not.

## Consequences and known limits

- SonarQube Community Build has no branch or pull request analysis: there a scan of a pull
  request is recorded as the main branch. SonarQube Cloud detects the pull request from the
  Actions environment. With a Community server, keep `SONAR_TOKEN` out of pull request runs.
- Pull requests from forks and from Dependabot get no secrets, so they are never scanned; the
  push to `main` after the merge is.
- `cancel-in-progress` also cancels a superseded run on `main`; the newer commit is scanned.
- Five jobs install five times; the npm cache makes that cheap, and a failure stays readable.
